# Lab conventions

How every session folder in this repository is organised. Keep it consistent so students always know where to look.

## Language and tone
- Everything in this repository is in **English** (READMEs, notebooks, code, comments).
- Short sentences, concrete steps, real API names. Link the official docs page for every concept used.

## Session folder (each session is an independent lab)
```
sessions/NN_<slug>/
  README.md          short: goal, notebooks table, setup, keys, troubleshooting, references (details live in the notebooks)
  pyproject.toml     dependencies with exact pins, `requires-python = "==3.12.*"`, `[tool.uv] package = false`
  uv.lock            generated by `uv lock`; commit it
  .python-version    3.12
  .env.example       only the keys this session reads (code loads `.env` from this folder)
  .vscode/           settings.json (default interpreter = the session venv) + extensions.json (Python, Jupyter)
  notebooks/         01_<part>.ipynb, 02_<part>.ipynb … full solution + outputs of a real run; images/ for diagrams
  app/               optional: code outside notebooks (servers, helpers); or one named package at the root
                     when the lab teaches it as a package (e.g. research_evals/)
  data/ tests/       optional: fixtures, pytest
  docs/              optional: step-by-step how-tos per part (connecting external apps, OAuth sign-in); no instructor notes
  output/            git-ignored files the code writes
```
Environment name: `venv<COURSE><NN>`, with `<COURSE>` the course code (`AE` Agent Engineering, `AO` AgentOps, …) and
`<NN>` the session number: `venvAE02`, `venvAO05`. Create it in the session folder with
`export UV_PROJECT_ENVIRONMENT=venvAE02 && uv sync` (PowerShell: `$env:UV_PROJECT_ENVIRONMENT="venvAE02"; uv sync`) and register it
with `uv run python -m ipykernel install --user --name venvAE02 --display-name venvAE02`. Every other command is `uv run …`
in the same terminal (identical on every OS). Students open the session
folder in VS Code or Cursor (Python + Jupyter extensions) and select that kernel; notebooks set `kernelspec` to it.
`ipykernel` is a dependency of every lab. The root README holds only the syllabus and the shared install (uv, git, IDE);
never list lab status there.
A session never imports from another session folder: copy the small part it builds on (and name the source session in a
comment). Keep core library versions identical across sessions.

## README template (keep it short)
1. **Goal**: two or three sentences and the diagram of what you build.
2. **Notebooks**: table (notebook, what you do).
3. **Setup**: environment, kernel, API keys (where to get each key, step by step), run.
4. **Troubleshooting**: the common mistakes.
5. **References**: official docs used.

## Code style (all labs)
- Every notebook's first code cell sets up logging, then checks the keys it needs:
  ```python
  logging.basicConfig(level=logging.INFO, format="%(levelname)s | %(message)s")
  for noisy in ("httpx", "httpx2"):  # HTTP clients log every request at INFO
      logging.getLogger(noisy).setLevel(logging.WARNING)
  logger = logging.getLogger(__name__)
  ```
  `logger.info` for progress while code runs (each node, tool call, decision), `logger.warning` for expected failures,
  `print` only for results the reader must see (answers, drafts, files).
- Section banners in long cells: `# ── Tools ─────…`. Short functions, docstrings, comments that explain design choices.
- Nothing machine-specific: relative paths from the notebook or `Path(__file__)`, keys from the session `.env`, no
  absolute paths in code or in saved outputs (never print `sys.executable` in a saved notebook).

## Rules
- Pin library versions in the session's `pyproject.toml`. Do not put dates in READMEs or notebooks.
- Labs use real services (LLM via `init_chat_model`, Tavily for search), configured only through `.env` (default model in
  `.env.example`). Keep calls cheap (few results) and state the keys needed in the README.
- Keep code simple and close to the official docs examples: same names and patterns, no extra abstractions.
- Execute every notebook top to bottom and **ship it with the outputs** of that real run, so readers can review it without
  running; versions are in `uv.lock`. Scenario cells pass the human replies as arguments, so the
  notebook runs without `input()`.
- Examples use topics unrelated to the framework being taught (it keeps outputs readable).
- When a notebook rebuilds a framework feature by hand (e.g. the agent loop), mirror the framework's own design and config
  (parallel tool calls with `Send`, `recursion_limit`), and say that the hand-built version exists to explain it.
- Embed diagrams as images (`notebooks/images/`) and draw graphs with `draw_mermaid_png()`; no ASCII diagrams.
- Never commit secrets. `.env` and `venv*/` are git-ignored; document every key in the session's `.env.example`.
- Output files the agent writes go to an `output/` folder next to the notebook (git-ignored).
- Each notebook is self-contained and runs top to bottom; markdown cells explain each step and link the docs.
